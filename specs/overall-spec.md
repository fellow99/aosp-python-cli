## 1. 系统目的与目标用户

### 1.1 一句话

本系统交付**可在 Android 终端里以独立进程运行的 `python` / `pip` 命令行**——以一个可发布的 Android 库容器为载体，附带一套可复现的构建、校验与发布流水线；它**不含任何嵌入 API**。

### 1.2 目标用户

| 用户 | 他们要什么 | 本系统给什么 |
|---|---|---|
| **终端应用开发者**（消费方） | 让用户在自己的 App 终端里敲出真的 `python` / `pip` | 一个声明依赖即可获得解释器与随包标准库的容器包；执行位与打包口径已按平台规则固化 ✅ |
| **终端最终用户** | 设备上可用的 python/pip | 经宿主终端启动的独立进程解释器（回程验证属 M2 ⬜规划 §7.1） |
| **仓库维护者** | 二进制可复现、供应链可审计 | 唯一事实源 + 门禁 + 幂等投放 + 不入库纪律 ✅ |
| **发布管理员** | 绝不误发、凭据不泄露 | 发布默认关闭 + 用户级凭据 + 两段式发布（规划 §10.1）✅发布面/⬜首发 |
| **合规评审者** | 许可齐备、无越权组件 | 第三方许可清单 ✅；完整全文随 Release 归档 ⬜ |

## 2. 系统边界

### 2.1 在范围内

| 域 | 内容 | 现状 |
|---|---|---|
| 构建骨架 | 工程结构、容器模块、打包口径（物理落盘）、版本纪律 | ✅（FR-000-001~005） |
| 事实源 | 版本/摘要/门禁/出处的唯一记录与 draft 纪律 | ✅（FR-000-010~013） |
| 投放与门禁 | 候选二进制的形态校验、来源校验、幂等投放、禁入清单 | ✅（FR-000-030~036） |
| 持续集成（配置期） | 无产物也可验证工程健康；脚本语法与退出码纪律自检 | ✅（FR-000-040~042） |
| 交叉编译 | 官方路径构建解释器本体与随包数据 | ⬜规划（规划 §4，M1） |
| 随包数据供给 | 标准库/包管理器树/CA 证书随容器分发并带清单校验 | ⬜规划（规划 §5，M1） |
| 发布 | 先行归档发布 + 中央仓发布两段式 | 发布面就绪 ✅ / 首发与归档发布 ⬜规划（规划 §10.1） |

### 2.2 不在范围内（规划 §1.3，能力边界）

1. **任何嵌入 API / 进程内解释器**——出现真实需求另立 `aosp-python-runtime` 线。
2. **pip 装 sdist / 含 C 扩展的 wheel**——设备无编译器，且静态解释器不能加载新原生件（能力边界，必须对消费方写明）。
3. **tkinter/curses/readline 类 UI 模块**——首版不编（⬜规划 §4.2）。
4. **python 环境管理**（venv 组合等）——归消费方/环境引导层。
5. **uv 本体**——属 `aosp-uv-cli`；本仓只与之组合。
6. **设备侧环境引导**（随包数据物化、环境变量注入）——消费方职责；本仓只定义契约（规划 §7）。
7. **node 系引擎供给**——引擎库由配对运行时仓统一供给；本容器**永久禁止**同名引擎库混入（门禁强制 ✅）。

### 2.3 交付边界

一次分发必须包含：容器包（原生可执行 + 随包数据 + 清单）、事实源记录、投放/校验工具、许可清单。**不得**包含：原生二进制的源码仓库副本（不入库）、任何嵌入 API 面。

## 3. 功能需求（按域索引，RFC 2119；编号沿用 FR-000-xxx）

### 3.1 构建骨架域（FR-000-001~005）

| 编号 | 级别 | 需求（WHAT/WHY） | 可证伪验收判据 | 现状 |
|---|---|---|---|---|
| FR-000-001 | MUST | 工程是单一模块容器工程：根工程名唯一标识本仓，且只包含一个库模块——多模块会让发布面与事实源复杂化 | 工程配置枚举出的模块列表恰为一项；根名与仓名一致 | ✅ |
 | FR-000-002 | MUST | 容器模块以 Android 库形态构建，目标 ABI 仅 AArch64，兼容到 API 24——单架构是发布红线，低 API 下限决定可执行兼容面 | 构建产物元数据显示单一 ABI、minSdk 24；构建系统任务图在该模块上可求值（TC-01） | ✅ |
| FR-000-003 | MUST | 制品版本 = 工具上游（CPython）版本，独立 semver，与 node 系无配对——解释器与引擎无 ABI 耦合，配对只会制造假约束 | 未提供版本时构建必须失败（不猜版本）；坐标版本等于所设版本 | ✅ |
| FR-000-004 | MUST | 原生件打包必须物理落盘（legacy packaging）——exec 型产物不落盘则无法启动（execve ENOENT）；这是与 dlopen 库相反的硬口径 | 打包配置该项为 true；注释保留理由，回归即评审否决 | ✅ |
| FR-000-005 | MUST | 二进制缺失不阻碍配置期——骨架先于产物存在，CI 与新成员在无产物机器上必须可用 | 无任何 `.so` 时任务图求值成功 | ✅（TC-01） |

### 3.2 唯一事实源域（FR-000-010~013）

| 编号 | 级别 | 需求 | 可证伪验收判据 | 现状 |
|---|---|---|---|---|
| FR-000-010 | MUST | 版本 + 大小 + 摘要 + 门禁 + 出处只记录在一处（锁文件），其它文件引用不复制 | 工具启动读锁；锁中不存在的版本/ABI 组合必须报错而非猜测 | ✅ |
| FR-000-011 | MUST | draft 记录不得伪造哈希：无实测值就留空/零/TBD | 现行 draft 条目 size=0、摘要为空串；任何工具不得把空值当通过依据 | ✅ |
| FR-000-012 | MUST | 门禁键集合反映 exec 型 profile：解释器键=系统动态链接器、依赖键=白名单制 | 锁文件门禁键含「系统解释器」与「依赖白名单」两键 | ✅ |
| FR-000-013 | MUST NOT | 事实源中不得出现与 node 系的配对字段 | 锁文件无 pairedRuntime 类字段 | ✅ |

### 3.3 投放与门禁域（FR-000-030~036）

| 编号 | 级别 | 需求 | 可证伪验收判据 | 现状 |
|---|---|---|---|---|
| FR-000-030 | MUST | 投放与门禁工具只认锁文件记录的版本/ABI 组合 | 请求未登记组合 → 明确报错并列出现有条目 | ✅ |
| FR-000-031 | MUST | 门禁为 exec 型七项：PIE 形态、恰一个系统动态链接器、AArch64、依赖白名单、摘要一致、大小一致、16KB 页对齐 | 对不合格二进制逐项打印 ✔/✘ 并以退出码 2 终止 | ✅（draft 期摘要/大小只记录不比对） |
| FR-000-032 | MUST | 退出码三值：0 全过 / 2 门禁不合格或未投放 / 1 用法或 IO 错误 | 三类场景实测退出码各归其位（TC-04/05） | ✅ |
| FR-000-033 | MUST | 门禁不合格 ⇒ 拒绝投放（先校验后复制，不合格不落盘） | 不合格输入投放后目标处无文件 | ✅ |
| FR-000-034 | MUST | 投放幂等且目标唯一：只投放锁内命名的那个二进制到锁内 ABI 目录 | 重复执行结果一致；目录内出现第二个 `.so` 即校验失败 | ✅ |
| FR-000-035 | MUST | 引擎库禁入：包内永不允许出现 node 系引擎同名库 | 投放/校验路径检测到即报错；`--check` 同时拒绝目录内任何兄弟原生件 | ✅ |
| FR-000-036 | SHOULD | 投放成功写入版本元数据（版本/ABI/名称/大小/摘要/时间），供容器资源面消费 | 元数据文件存在且字段与锁和产物一致 | ✅ |

### 3.4 持续集成（配置期）域（FR-000-040~042）

| 编号 | 级别 | 需求 | 可证伪验收判据 | 现状 |
|---|---|---|---|---|
| FR-000-040 | MUST | CI 在无产物机器上验证工程健康：任务图求值必须成功 | 干净 runner 上配置门禁通过 | ✅ |
| FR-000-041 | MUST | CI 自检投放工具的退出码纪律：未投放态必须得到 2，其它非零码视为工具缺陷 | CI 内显式断言退出码=2 | ✅语义已定义；⚠️ 断言脚本在失败即停的 shell 下按失败退出（症状同为失败但文案不符）——登记于 `000-scaffold/plan.md` §9，M1 重写流水线时修复 |
| FR-000-042 | MUST | 全部工具脚本入 CI 语法门禁（JS 语法检查 + shell 语法检查） | CI 步骤对每个脚本执行语法检查且通过 | ✅ |

### 3.5 交叉编译与随包数据域（⬜规划，M1——规划 §4/§5，本文仅登记边界）

- 官方路径交叉编译、扩展全静态、TLS 与 sqlite 静态链入、包管理器树随包 + 壳命令入口：**全部为规划设计**，未实现；其验收判据（G1/G2）见规划 §10，真机回程探针见规划 §7.1（⬜M2）。
- 需求侧不变式（已从 M0 固化）：产物必须过 3.3 全部门禁；随包数据必须带逐文件清单与总摘要（规划 §5 manifest）；静态性检查（数据树内不得出现原生件）（规划 §6）。

## 4. 非功能需求

| # | 需求 | 判据 | 现状 |
|---|---|---|---|
| NFR-1 | **可复现**：干净环境单条流水线重出同口径产物（G4） | 锁回写后二次构建摘要一致 | ⬜规划（M1） |
| NFR-2 | **零依赖可跑**：门禁/投放工具在仅有 JS 运行时的机器上可用 | 不引入任何第三方包；CI 未装额外运行时仍通过 | ✅ |
| NFR-3 | **单架构红线**：只发布 AArch64 | 构建与锁两处 ABI 白名单一致 | ✅ |
| NFR-4 | **防误发**：发布动作默认不可达；凭据不进仓库 | 默认配置下发布任务全部禁用；仓库内只有凭据模板 | ✅ |
| NFR-5 | **可审计**：一次 diff 能看清版本/哈希/出处变化 | 事实源为纯文本入库、二进制不入库 | ✅ |
| NFR-6 | **如实汇报**：未实测项一律标 ⬜，不得当作既定事实 | 文档与锁文件无「未测装已测」 | ✅ |
| NFR-7 | **快速反馈**：配置期 CI 不得拖慢骨架迭代 | 超时上限 20 分钟量级 | ✅ |

## 5. 用户故事（验收视角）

1. **作为消费方开发者**，我声明依赖本容器包并给出随包数据目录，我的终端即可启动 python 子进程——我**不**需要理解 ELF、SELinux 或打包细节（打包口径已在本仓固化 ✅；环境注入契约见规划 §7 ⬜）。
2. **作为仓库维护者**，我拿到一个候选二进制后，一条命令即可知道它能不能进包：七项门禁逐项给出 ✔/✘，不合格绝不落盘（✅）。
3. **作为发布管理员**，我在不携带任何凭据的机器上构建/测试时，发布任务必须全部不可达（✅）；真实发布只在我配置了用户级凭据并显式打开开关时发生（✅发布面/⬜首发）。
4. **作为合规评审者**，我能在仓库里找到一个随包分发组件与许可的完整清单（✅），并在发布归档中找到许可全文（⬜规划）。
5. **作为新加入的工程师**，我在没有构建产物的新机器上 clone 后，CI/本地都能验证工程是健康的（✅），并从 specs 索引找到所有契约文档（✅本套）。
